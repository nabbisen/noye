# Requirements traceability

This document maps each functional and non-functional requirement from the original specification to its implementation in the codebase.

## 2-1. Authentication and access control

| Requirement | Status | Implementation |
|---|---|---|
| Generic OIDC client (Authorization Code + PKCE + state + nonce) | Done | `crates/gateway/src/auth/oidc.rs` |
| OIDC Discovery with KV cache | Done | `crates/gateway/src/auth/oidc.rs::discover` |
| ID Token signature verification (RS256/RS384/RS512/PS256/ES256/ES384) | Done | `crates/gateway/src/auth/crypto.rs::verify_jwt_signature` |
| Provider-agnostic configuration | Done | `OIDC_ISSUER_URL` env var only |
| KV-backed sessions with HttpOnly + Secure + SameSite=Lax cookies | Done | `crates/gateway/src/auth/session.rs`, `auth/cookie.rs` |
| RBAC (`admin` / `member`), managed in D1 | Done | `crates/gateway/src/auth/rbac.rs`, `users` table |
| No guest users (unregistered emails are rejected at login with 403) | Done | `lib.rs::handle_auth_callback` checks `core_client::lookup_user` before issuing a session |

## 4. Operational requirements

| Requirement | Status | Where |
|---|---|---|
| Audit log: time, actor, target, change, result | Done | `audit_logs` table; `db::audit::log` and `log_system`. Tamper detection via SHA-256 hash chain (since 0.18.0): each row carries `prev_hash` + `row_hash`, breaking the chain on any subsequent `UPDATE` / `DELETE` / out-of-order insert. `GET /api/admin/audit/verify` (admin-only) walks the chain and reports mismatches. See `security-posture.md#audit-log-tamper-detection`. |
| CSRF protection on state-changing endpoints | Done | Synchronizer Token Pattern (since 0.19.0). 32-byte session-bound token generated at login, surfaced via `<meta name="csrf-token">` in every authenticated HTML page, required as `X-CSRF-Token` header on every `POST` / `PUT` / `DELETE`. Constant-time comparison in `gateway::auth::csrf::constant_time_eq`. Legacy session opt-out (allows once with `console_log` warning) avoids deploy-day lockout; `GET /auth/logout` exempted for UX. See `security-posture.md#cross-site-request-forgery-csrf`. |
| Self-service security page (active sessions, force-logout, login history, audit verify UI) | Done | `/me/security` (since 0.20.0). Stats page replaces the `<form><select><button>` window selector with a `tabs` widget (URL-driven, no JS, bookmarkable), adds a per-row CSV export link to the per-target table, and surfaces the "Gross uptime vs SLA uptime" interpretation alongside the table. |
| UI/UX redesign of "Operate" pages (Targets / Channels / Maintenance) | Done (Phase C of UI/UX rework — 0.25.0) | Target detail page split into four URL-driven tabs (`?tab=overview\|results\|channels\|settings`) so an operator answers one question at a time: "what is this check?" / "is it healthy right now?" / "who gets paged?" / "what are the knobs?". ## Roadmap (deferred / not yet implemented)

These items are recognized gaps. They are intentionally listed here rather than in a separate file so the requirements document stays the single source of truth for "what the project promises and what it actually delivers."

| Item | Status | Rationale and notes |
|---|---|---|
| Email delivery on alert | Done | `notify::email` module with config loader (`load_config`), validator (`is_valid_email`), MessageBuilder factory (`build_message`), and `send_email` driving `wasm-smtp` 0.9.3 + `wasm-smtp-cloudflare` 0.9.3 + `mail-builder` 0.4 (mail-builder integration since 0.22.0; wasm-smtp 0.9.3 since 0.21.0; previously 0.6.0 since 0.17.0). Composition (RFC 5322 / RFC 2047 / MIME) is handled by `mail-builder` rather than hand-rolled — `client.send_message(...)` consumes a `MessageBuilder` and serializes via `write_to_string`. Both Implicit TLS (port 465) and STARTTLS (port 587) supported with port-based auto-detection plus an explicit `EMAIL_SMTP_TLS_MODE` override. Authentication auto-selects the strongest mechanism the server advertises: `SCRAM-SHA-256` (RFC 7677, default-on since wasm-smtp 0.9.0) > `PLAIN` > `LOGIN`. Configuration via the standard Wrangler vars/secret split. Test-send returns precise diagnostics ("not configured" / "misconfigured: <reason>" / actual SMTP error message) rather than silently succeeding. See [email-delivery.md](email-delivery.md). Provider-API alternatives (SendGrid, Resend, Mailgun HTTPS APIs) are intentionally deferred as a lower-priority separate item. |
| Email delivery via transactional API providers (SendGrid / Resend / Mailgun / SES API) | Not implemented (low priority) | The `wasm-smtp` route covers any plain SMTP-AUTH relay including these providers' SMTP endpoints, so a separate HTTPS-API integration is unnecessary for the foreseeable future. Would only become valuable if we needed provider-specific features like template rendering or bounce-event ingestion. |
| Long-window SLA snapshots | Not implemented | The SLA calculator runs on demand against the live `incidents` table. For a 90-day window with hundreds of incidents this is fine; for year-plus windows on a busy deployment, latency would grow linearly. The remediation, when needed, is a periodic snapshot table populated by a daily Cron — out of scope until a real deployment hits the limit. |
| Integration tests against a live Worker runtime | Partial | The WASM-runtime layer is now covered: `cargo test -p noye-gateway --target wasm32-unknown-unknown` runs 12 tests against `auth::crypto::*` using `wasm-bindgen-test` (see [development.md](development.md#wasm-target-tests)). Verifies SHA-256 (FIPS 180-4 vectors), RNG, base64url round-trip, and RS256 signature verification (RFC 7515 §A.2 vectors) against real Web Crypto. The Workers-binding layer (D1, KV, Service Bindings) still requires Miniflare or a future `worker::testing` harness and remains deferred. |
| CI configuration | Not implemented | A GitHub Actions workflow that runs `cargo check --workspace` and `cargo test --workspace --lib` on every push would catch regressions earlier. Separate from the integration-test question. |
| Cargo.lock committed to source control | Not implemented | Currently `.gitignored`. Committing it would make builds reproducible across environments and make `wrangler deploy` output deterministic. |

The email-delivery decisions previously listed here have been resolved in
favour of a single shared SMTP relay via the `wasm-smtp` crate (active as of
0.17.0 with 0.6.0; upgraded to 0.9.3 in 0.21.0 to pick up SCRAM-SHA-256;
RFC 5322 / MIME composition delegated to `mail-builder` in 0.22.0).
See [email-delivery.md](email-delivery.md) for the configuration walkthrough,
the provider table, and the build-time `.cargo/config.toml` requirement that
the 0.9.x line introduced.
